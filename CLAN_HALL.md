## 1. Суть

У каждого клана (`clans.kind = 'clan'`) может быть одно клановое здание.
Кнопка «🏰 Здание клана» в карточке клана доступна **любому члену**:

- здание не выбрано → страница выбора из трёх вариантов;
- идёт сбор/стройка/апгрейд → страница прогресса;
- построено → страница здания с входом внутрь.

Внутри — расширения (кухня, крафтовый стол, душевые, сад, библиотека рецептов,
клановая лавка), доступные всем членам клана.

## 2. Три уровня здания

| Тип | Ключ | Слотов расширений | Макс. уровень расширения | Время |
|---|---|---|---|---|
| Дом Клана | `house` | 2 | 2 | 2 дня |
| Клановое поместье | `manor` | 4 | 2 | 4 дня |
| Индивидуальный проект резиденции клана | `castle` | 7 | 4 | 7 дней |

- 7-й слот резиденции — **резерв** под будущие механики, сейчас ничем не занимается.
- Тип можно **улучшать** по той же механике: ресурсы со склада + оплата НМ лидером,
  время — **целевого уровня** (Дом→Поместье 4 дня, Поместье→Резиденция 7 дней).
- **Оплата без ресурсов:** глава может не копить ресурсы на складе, а оплатить
  работы в **двойном размере** (`price_nm × CLAN_BUILDING_NO_RESOURCES_MULT`):
  6000 / 16000 / 40000 НМ. Ресурсы со склада при этом не списываются.
- Во время улучшения здание **остаётся доступным**, но картинка меняется на
  «стройку». Использование уже установленных расширений не блокируется,
  установка/улучшение расширений — блокируется до завершения.
- Понижения уровня нет.

## 3. Модель данных

Новые таблицы добавляются в `database/db.py::init_db()` (через `executescript`,
`CREATE TABLE IF NOT EXISTS`). `MIGRATIONS.md` обновится автоматически,
`db_schema.md` — **вручную**.

### 3.1 `clan_buildings` — состояние здания (1 строка на клан)

| Колонка | Тип | Смысл |
|---|---|---|
| `clan_id` | INTEGER PRIMARY KEY | клан |
| `building_type` | TEXT | текущий тип (`house`/`manor`/`castle`) или `NULL` |
| `target_type` | TEXT | цель апгрейда; `NULL` если апгрейда нет |
| `status` | TEXT | `choosing` / `funding` / `building` / `upgrading` / `built` |
| `required_json` | TEXT | снимок требований проекта `{"Доска": 60, ...}` |
| `price_nm` | INTEGER | снимок цены проекта |
| `chosen_at` | TIMESTAMP | когда выбран тип |
| `started_at` | TIMESTAMP | когда начата стройка/апгрейд |
| `completes_at` | TIMESTAMP | когда завершится |
| `updated_at` | TIMESTAMP | служебное |
| `building_photo_file_id` | TEXT | индивидуальное фото готового здания клана (добавляет админ после постройки; на время стройки/апгрейда показывается общая заглушка `settings.clan_construction_photo`) |

Строка создаётся лениво при первом открытии холла (`status='choosing'`).

### 3.2 `clan_storage` — общий котёл клана

| Колонка | Тип |
|---|---|
| `clan_id` | INTEGER NOT NULL |
| `item_id` | INTEGER NOT NULL |
| `qty` | INTEGER NOT NULL DEFAULT 0 |
| `updated_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP |

PK `(clan_id, item_id)`. Хранит **любые** ресурсы; излишки не сгорают и
остаются на будущие стройки/апгрейды.

### 3.3 `clan_build_contrib` — журнал вкладов (для прозрачности)

| Колонка | Тип |
|---|---|
| `id` | INTEGER PRIMARY KEY AUTOINCREMENT |
| `clan_id` | INTEGER NOT NULL |
| `user_id` | INTEGER NOT NULL |
| `item_id` | INTEGER NOT NULL |
| `qty` | INTEGER NOT NULL |
| `created_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP |

Журнал не даёт механике возврата (вклады невозвратны), но нужен для
разбирательств и статистики «кто сколько вложил».

### 3.4 `clan_expansions` — слоты расширений

| Колонка | Тип |
|---|---|
| `clan_id` | INTEGER NOT NULL |
| `slot_index` | INTEGER NOT NULL |
| `expansion_type` | TEXT NOT NULL |
| `expansion_level` | INTEGER DEFAULT 1 |
| `installed_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP |

PK `(clan_id, slot_index)`. **Один тип расширения — только один раз**
(проверка в коде + уникальный индекс по `(clan_id, expansion_type)`).

### 3.5 `clan_recipes` — библиотека рецептов клана

| Колонка | Тип |
|---|---|
| `clan_id` | INTEGER NOT NULL |
| `recipe_id` | INTEGER NOT NULL |
| `donated_by` | INTEGER |
| `created_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP |

PK `(clan_id, recipe_id)`. Не путать с личными `user_recipes`.

### 3.6 `clan_garden` — общий сад

| Колонка | Тип |
|---|---|
| `clan_id` | INTEGER NOT NULL |
| `plot_index` | INTEGER NOT NULL |
| `user_id` | INTEGER | кто посадил |
| `plant_data` | TEXT DEFAULT '{}' |
| `updated_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP |

PK `(clan_id, plot_index)`.

### 3.7 `clan_shop_items` — витрина клановой лавки

| Колонка | Тип |
|---|---|
| `clan_id` | INTEGER NOT NULL |
| `item_id` | INTEGER NOT NULL |
| `price` | INTEGER NOT NULL |
| `stock` | INTEGER DEFAULT -1 |
| `is_active` | INTEGER DEFAULT 1 |

PK `(clan_id, item_id)`. Сюда админским методом добавляется клановая накидка
(личный предмет каждого клана) и, при необходимости, точечные товары.

## 4. Потоки

### 4.1 Выбор типа здания (лидер)

1. Лидер открывает «Здание клана» → `status='choosing'`.
2. Видит три варианта: ресурсы, цена НМ, время, число слотов.
3. Нажимает «Выбрать» → `building_type`, `status='funding'`, фиксируются
   `required_json` и `price_nm` (снимок: будущие правки баланса не ломают проект).
4. Сменить тип можно **только пока в клановый склад не внесено ни одного
   ресурса под проект**; иначе тип блокируется до завершения.

### 4.2 Склад и вклады

- Любой член клана жертвует предметы из личного инвентаря: `+1`, `+10`, «всё».
- Вклад невозвратен. Списание из инвентаря атомарно с записью в `clan_storage`
  и `clan_build_contrib`.
- На вкладке строительства видно прогресс по каждому ресурсу:
  `Доска 42/60`, `Железная руда 15/15` и т.д.
- Лишнее сверх требований не запрещается — остаётся на складе.
- Вывод со склада в v1 **не делаем**. Хелпер `can_withdraw_clan_storage(clan_id, uid)`
  пока возвращает `True` только главе; права иерархии подключим следующим этапом.

### 4.3 Старт строительства (лидер)

**Вариант 1 — с ресурсами.** Условия: `status='funding'`, все требования покрыты
`clan_storage`, у лидера хватает НМ (базовая `price_nm`).

Действие:
1. Списываются ровно требуемые количества со склада (излишки остаются).
2. Списываются НМ с лидера (транзакция `clan_build`).
3. `status='building'`, `started_at=now`, `completes_at=now + дни`.
4. Уведомление всем членам клана: «Стройка начата, завершится …».

**Вариант 2 — без ресурсов (`clanh:startfull:<id>`).** Ресурсы на складе не нужны:
глава платит `price_nm × CLAN_BUILDING_NO_RESOURCES_MULT` (двойная цена — 6000 /
16000 / 40000 НМ), склад клана не трогается. Транзакция та же (`clan_build`),
в описании помечается «без сбора ресурсов (двойная оплата)». Кнопка доступна
главе на экране сбора всегда, независимо от наличия ресурсов; при нехватке НМ —
отказ с расчётом двойной цены.

Отмена на этапе `funding`: ресурсы **остаются** на клановом складе,
`status` возвращается в `choosing`, требования сбрасываются. Возврата в
инвентарь нет (вклад невозвратен).

### 4.4 Завершение и ленивое разрешение

- Хелпер `resolve_clan_building(clan_id)` вызывается при каждом открытии холла:
  если `now >= completes_at` — `building` → `built` (тип = выбранный),
  `upgrading` → `built` (тип = `target_type`).
- Суточный цикл `main.py::scheduled_jobs` дополнительно проходит по активным
  проектам и рассылает уведомления о завершении (и не даёт «просрочке» висеть,
  если в холл никто не заходил).
- Уведомления: старт стройки, завершение стройки, завершение апгрейда.

### 4.5 Вход внутрь

- Кнопка входа видна **только членам клана** (проверка `is_clan_member`).
- Внутри: картинка здания, список слотов расширений, склад (просмотр),
  кнопки «Внести ресурсы» (все) и «Управление» (лидер).

## 5. Расширения

Типы (одно на клан):

| # | Ключ | Название | Что даёт |
|---|---|---|---|
| 1 | `kitchen` | Кухня | готовка по выученным рецептам, гейт по уровню кухни |
| 2 | `workbench` | Крафтовый стол | крафт по выученным рецептам, гейт по уровню |
| 3 | `shower` | Душевые | +ОД раз в сутки **каждому** члену (личный кулдаун) |
| 4 | `garden` | Сад | общие грядки, урожай в клановый склад |
| 5 | `library` | Библиотека рецептов | книги/рецепты клана, доступны всем членам |
| 6 | `shop` | Клановая лавка | дешёвые расходники/оружие + накидка клана |
| 7 | — | резерв | под будущие механики |

Правила:

- **Установка** — бесплатна: лидер выбирает пустой слот и тип из доступных
  (лимит слотов по типу здания). Уже установленный тип не предлагается.
- **Улучшение** — мгновенно после оплаты: НМ лидера + ресурсы с кланового
  склада; максимум уровня — по типу здания (2/2/4). Стоимость — в
  `CLAN_EXPANSION_UPGRADE` (см. §7).
- **Крафт** (кухня/стол) — **личный**: ОД и ингредиенты пилота, результат ему.
  Клановое расширение даёт доступ и уровень, а не общий котёл. Защита от
  двойного крафта — существующий `CRAFTING` (per-user).
- **Рецепты** — пересечение личных `user_recipes` и `clan_recipes` (для
  библиотеки). Личные рецепты работают и без библиотеки, если у клана есть
  кухня/стол.
- **Душевая** — личный кулдаун `can_use_shower(uid)`, как в жилье.
- **Сад** — сажать может любой член (семя из личного инвентаря, `user_id`
  запоминается); **собирает только глава**, урожай уходит в `clan_storage`.
  Лимит грядок зависит от уровня расширения.
- **Библиотека** — предмет-рецепт (`items.category='recipes'`) сдаётся
  навсегда: списывается из инвентаря, пишется `clan_recipes`. Рецепт становится
  доступен всем членам. «Книги, открывающие несколько рецептов» — отдельный
  бэклог-пункт; текущая реализация работает с одним рецептом на предмет.
- **Лавка** — покупка только членам клана; цена из `clan_shop_items`;
  лимит покупок на пилота в сутки (защита экономики). Накидка — личный предмет
  каждого клана, добавляется админским методом в `clan_shop_items`.

## 9. Жизненный цикл и крайние случаи

- **Роспуск клана** (`clan_delete_yes_cb`): удаляются `clan_buildings`,
  `clan_storage`, `clan_build_contrib`, `clan_expansions`, `clan_recipes`,
  `clan_garden`, `clan_shop_items`. Всё сгорает — решение владельца.
- **Смена главы**: новый глава получает управление автоматически (проверки идут
  по `clans.leader_id`, не по автору постройки).
- **Лидер не оплатил**: проект висит в `funding` сколько угодно; ресурсы лежат
  на складе и не пропадают. Отдельного таймаута нет.
- **Уход лидера из клана**: управление переходит действующему главе; проект
  продолжается.
- **Одновременные действия**: старт стройки/апгрейда и установка расширений —
  проверять статус здания в момент действия (не только при отрисовке).
- **Дубликаты**: уникальный индекс `(clan_id, expansion_type)` не даёт поставить
  два одинаковых расширения даже при гонке.

## 9.1 Апгрейд здания (Фаза 2): вариант A — утверждён

> **Решение владельца (2026-10-25): вариант A.** Одна строка на клан:
> `building_type` — текущий уровень, `target_type` — цель апгрейда. Для сбора
> на апгрейд вводим статус `upgrade_funding`. После завершения апгрейда
> `building_photo_file_id` сбрасывается — показывается дефолтная картинка
> уровня, индивидуальное фото улучшенного здания админ загружает после стройки.
> Отдельный журнал истории (`clan_building_history`) **не заводим**.
>
> Вариант B (строка на проект) ниже оставлен как история обсуждения — не берём.

Игровой результат у обоих вариантов одинаковый, различается только **как это
лежит в БД и сколько кода придётся переписать**. Сначала — что видит игрок.

### Как выглядит апгрейд для игрока

1. Клан построил дом: `status='built'`, `building_type='house'`, 2 слота,
   расширения до 2 ур.
2. Глава открывает холл → «⬆️ Улучшить до Поместья». Фиксируется снимок
   **целевого** уровня: `manor`, 150/60/50 ресурсов, 8000 НМ, 4 дня.
3. Члены вносят ресурсы на склад, глава платит НМ (или двойную цену без
   ресурсов — та же кнопка `startfull`, что и при первой стройке).
4. Здание переходит в «идёт улучшение». Внутрь **по-прежнему можно**: работают
   те же 2 слота дома и лимит расширений 2 ур., нельзя только ставить/улучшать
   расширения.
5. По таймеру здание становится поместьем: 4 слота, лимит расширений 2 ур.,
   картинка — поместья. Дом как отдельная сущность больше не существует.

### Вариант A — одна строка, `target_type` как «куда улучшаемся»

Строка `clan_buildings` одна на клан (как сейчас, PK `clan_id`). Текущий уровень
всегда в `building_type`, цель — в `target_type`.

| Этап | `building_type` | `target_type` | `status` | `required_json` / `price_nm` |
|---|---|---|---|---|
| дом построен | `house` | `NULL` | `built` | пусто / 0 |
| выбран апгрейд | `house` | `manor` | `upgrade_funding` | снимок поместья |
| оплачен | `house` | `manor` | `upgrading` | снимок поместья |
| улучшение завершено | `manor` | `NULL` | `built` | пусто / 0 |

**Что уже готово под A:** `start_clan_upgrading()` уже пишет `target_type` +
`status='upgrading'` + `completes_at`; `resolve_clan_building_with_event()` уже
понимает `upgrading` и при завершении подставляет `target_type` в
`building_type`; `set_clan_building_built()` уже чистит `target_type`,
`required_json` и `price_nm`. То есть ядро таймера и завершения написано ещё в
Фазе 1 и покрыто косвенно. В Фазе 2 остаётся UI и ветки «сбор на апгрейд».

Нюансы, которые надо решить именно в A:

- **Сбор на апгрейд нельзя путать со сбором на первый дом.** У первого дома
  `building_type` задан, а `target_type = NULL`; у апгрейда — оба заданы.
  Чтобы экраны не угадывали по комбинации полей, предлагаю отдельный статус
  `upgrade_funding` (колонка `status` — свободный `TEXT`, миграция не нужна).
  Тогда: `choosing` → первый дом; `upgrade_funding` → сбор на апгрейд;
  `upgrading` → работы.
- **Отмена.** Для первого дома отмена → `choosing`; для апгрейда → назад в
  `built`, `target_type`/снимок очищаются, ресурсы остаются на складе. Значит,
  `cancel_clan_building()` получает одну ветку по статусу.
- **`chosen_at` и вклады.** `has_clan_project_contributions()` считает вклады
  после `chosen_at`; при выборе апгрейда `chosen_at` надо переставить на «сейчас»,
  иначе старые вклады от первой стройки заблокируют смену цели.
- **Снимок требований перезаписывается.** Для построенного дома
  `required_json`/`price_nm` уже не нужны (они относятся только к активному
  проекту), поэтому перезапись безопасна. Минус: история «сколько стоило
  поместье» нигде не остаётся — если нужна, добавляется отдельная append-only
  таблица `clan_building_history` (не влияет на живую модель).
- **Фото здания.** `building_photo_file_id` одно на клан. После апгрейда там
  останется фото дома. Варианты: (1) при завершении очищать и показывать
  дефолтную картинку уровня из `assets/img/clan/`, пока админ не загрузит новую;
  (2) хранить карту «уровень → file_id» в JSON; (3) оставлять старое до загрузки
  нового (риск: поместье с фото дома). Рекомендую (1) — проще и без «вранья».
- **Слоты и лимиты** читаются из `building_type` (текущий уровень), поэтому
  во время работ автоматически остаются старыми — это и нужно по спеке.
- **Проверки:** апгрейд только из `built`, только на уровень выше
  (`house → manor → castle`), только главой; нельзя два апгрейда сразу.

**Итог по A:** 0 изменений схемы и миграций; ~8–10 правок в хелперах и
хендлерах; один источник правды; риск рассинхрона почти нулевой. Оценка — ~1 день.

### Вариант B — отдельная строка на проект

`clan_buildings` превращается в журнал проектов: построенный дом — одна строка,
апгрейд — **новая** строка, старая помечается архивной. Во время работ в таблице
две живые строки: «текущее здание» и «проект улучшения».

Что придётся сделать:

- Убрать `PRIMARY KEY (clan_id)` (в SQLite это пересоздание таблицы), добавить
  `id`/`project_id`, `is_current`, `archived_at`, `kind` (`build`/`upgrade`).
- Частичный уникальный индекс `UNIQUE(clan_id) WHERE is_current = 1` — иначе
  легко получить два «текущих» здания.
- Все читающие хелперы (`get_clan_building`, `ensure_clan_building`,
  `resolve_*`, экраны холла, проверки слотов/лимитов расширений) переписать с
  «единственной строки» на «текущую строку + активный проект». Это главный
  источник регрессий: любой забытый запрос начнёт читать проект вместо здания
  (или наоборот).
- Завершение апгрейда — две записи в одной транзакции: проект → `built` +
  `is_current=1`, старое → `archived`. При сбое между ними нужна защита.
- Миграция прод-данных: для каждого клана пометить существующую строку
  `is_current=1`; пересоздание таблицы на живой БД.

Что даёт B:

- Единый **пишущий** путь: «выбрал цель → собрал → построил» буквально один и
  тот же код для первого дома и апгрейда, без ветки `upgrading`.
- Естественная история: когда и что построено, за сколько, с каким фото.
- Фото и снимок требований хранятся у проекта, старые не затираются — вопрос
  «фото после апгрейда» решается сам.

Чего B **не** решает: читающая сторона всё равно обязана отличать текущее
здание от проекта (нельзя показывать 4 слота поместья, пока идёт стройка),
поэтому «единый код» получается только в записи. Плюс выше цена ошибки:
схема, миграция и все запросы.

**Итог по B:** пересоздание таблицы + переписывание читающих хелперов;
~1,5–2 дня и заметно выше риск регрессий. Оправдано, если история/фото по
уровням — обязательное требование, а не «когда-нибудь пригодится».

### Сравнение

| Критерий | A (одна строка) | B (строка на проект) |
|---|---|---|
| Изменения схемы | нет (только новый статус) | пересоздание таблицы, новые колонки и индекс |
| Миграция прод-БД | не нужна | нужна, с бэкапом |
| Переписать хелперов | 1–2 (`cancel`, выбор апгрейда) | почти все читающие + `resolve` |
| Источник правды | один — строка клана | две строки, нужен `is_current` |
| Риск рассинхрона | низкий | средний/высокий |
| История и фото по уровням | нет (можно добавить лог) | есть «из коробки» |
| Единый код первого дома и апгрейда | нет (ветка `upgrading`) | да, но только на записи |
| Оценка | ~1 день | ~1,5–2 дня |

### Рекомендация

Берём **A**: схема и половина механики уже под неё написаны, она дешевле и
надёжнее. Историю, если понадобится, добавим отдельной append-only таблицей
`clan_building_history` — это не меняет живую модель и не требует миграции
существующих запросов. Фото после апгрейда — сбрасывать на дефолт уровня.

### Решение (2026-10-25)

1. **Вариант A** — одна строка + `target_type`, новый статус `upgrade_funding`.
2. **Фото** после апгрейда сбрасывается на дефолтную картинку уровня; своё фото
   улучшенного здания админ загружает уже после завершения стройки.
3. **Журнал истории не нужен** — `clan_building_history` не заводим.

Фаза 2 стартует по варианту A. Вариант B остаётся в этом разделе только как
история обсуждения.

## 11. План тестов

- Схема/хелперы: ленивое создание строки, снимок требований, излишки склада.
- Вклады: списание из инвентаря, запись в журнал, запрет отрицательных вкладов.
- Старт: без полного склада — отказ; без НМ — отказ; успех — списание ровно
  требуемого, излишки на месте. Оплата без ресурсов: двойная цена, склад не тронут.
- Завершение: ленивое разрешение по времени, уведомления, повторный вызов идемпотентен.
- Апгрейд: тип меняется только после таймера, доступ не пропадает, слоты
  расширяются, лимит уровня растёт.
- Расширения: один тип один раз, лимит слотов, лимит уровня, апгрейд списывает
  НМ и ресурсы, при нехватке — отказ.
- Крафт: личные ОД/ингредиенты/результат; гейт по уровню расширения; кухня и
  стол не мешают друг другу; `CRAFTING` не даёт двойной крафт.
- Душевая: +ОД каждому члену, личный кулдаун.
- Сад: посадка любым, сбор только главой, урожай в склад.
- Библиотека: книга списывается навсегда, рецепт доступен всем, повторная
  сдача отклоняется.
- Лавка: покупка только членам, цена клановая, дневной лимит.
- Роспуск: все таблицы чисты.
- Партия: холл недоступен.
